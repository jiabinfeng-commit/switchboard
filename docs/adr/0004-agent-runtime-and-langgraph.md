# ADR 0004：Agent 运行时与 LangGraph 的边界

- 状态：草案（切片 3）
- 日期：2026-11-10
- 关联：ADR 0001（输出契约）、ADR 0002（流程编排）、ADR 0003（执行恢复）

## 背景

项目重心从业务流程编排转向 Agent 编排与评测。ADR 0002 已定两层分工：
跨小时/天的流程用自研引擎，单步内部的规划与工具调用用 LangGraph。
但「单步内部」具体指什么、哪些能力不能放进图里，之前只有一句话，容易在
实现时把等待、重试、人工介入都画进 LangGraph，最终得到两个流程引擎。

切片 2b 已完成，业务编排停在可用的位置：能表达 agent 步骤、等待、人工任务、
崩溃恢复。它作为宿主，不再继续加功能。

## 决策

### 1. 判据是「要不要等」

- 要等的：等人回复、等定时器、等外部工单状态。跨度小时到天，进程会重启。
  **归外层流程引擎。**
- 一口气跑完的：一次模型调用加若干轮工具调用，几十秒内结束。
  **归 AgentRuntime，内部可以用 LangGraph。**

写内部时不知道实例、时间、挂起；写外部时不知道图长什么样。

### 2. AgentRuntime 的契约

```python
class AgentRuntime(Protocol):
    def run(self, step_input: StepInput, idempotency_key: str) -> StepResult: ...
```

输入输出沿用 ADR 0001：`StepInput` 包含模型视图、工具白名单、身份边界；
`StepResult` 是五类动作之一，外加 `may_have_committed`、`cause`、`evidence`、
`payload`。运行时内部可以有任意多轮循环，对上游不可见；内部循环用尽后
只交回一个 `StepResult`。

`idempotency_key` 由外层执行记录提供（ADR 0003）。运行时**不消费**它，
只透传给需要写操作的下游——第一版 agent 内部工具必须只读，所以实际用不到，
接口先留出来是为了将来允许幂等写操作时不改契约。

### 3. LangGraph 图内的四条约束

1. **状态只放本次步骤的临时数据**：消息、工具结果、候选假设、校验失败次数。
   不放实例 id、身份、流程上下文；这些由 `StepInput` 进入，用完即弃。
2. **工具只读**。建单、派单、改状态等写操作放在外层的 `tool` 节点，
   这样整步重跑不会重复副作用。
3. **内部循环有预算**：最大轮数、最大工具调用次数、最大 token。
   用尽返回 `need_human` 或 `retryable`，不能无限转。
4. **图不跨挂起**。需要人等或外部事件的节点是外层的 `wait_*`，
   不是 LangGraph 的 `interrupt`。

### 4. 第一版不用 checkpointer

内部崩溃时 `run()` 没有返回，外层执行记录停在 `started`；恢复时用同一个
幂等键整步重跑。恢复责任在外层，不在图里。

代价是重新调模型、浪费 token。可接受的前提是内部工具只读（决策 3 第 2 条）。
checkpointer 买的是「从图中间继续」，带来第二套持久化状态：图的 checkpoint
说执行到某节点，外层记录说步骤未完成，必须额外定权威。第一版不付这个成本。

升级条件（满足任一才考虑）：单步稳定运行超过几分钟；中间有昂贵且可复用的
计算结果；整步重跑的成本高到不可接受。升级时外层仍是权威，checkpoint 只做
加速，丢失即从头跑。

### 5. 不用 interrupt 做跨天人工介入

`interrupt` 是会话内的人工介入：暂停几十秒到几分钟，让用户确认一个有风险的
动作。它依赖图的 thread 状态持久化才能跨调用的恢复。

服务台的人工介入是另一回事：等用户补信息可能一天，等工程师处理可能两天，
期间要能列出待办、要能超时、进程重启后要能恢复。这些由外层的 `wait_user`
和 `human_task` 承担（ADR 0002、0003）。

两者混用会出现两个等待机制：外层实例挂着，图的 thread 也暂停着，恢复时
先恢复谁、以谁为准都要额外定规则。同一个问题不要有两套状态源。

### 6. 多 agent 的升级阶梯

多 agent 是手段不是目标。默认单 agent 加工具循环。出现下列信号之一才拆：

1. 一个 prompt 同时承担提取、检索、生成、校验，改一处坏另一处；
2. 不同子任务需要不同权限或不同工具集；
3. 单模型自检效果差，需要独立的 critic；
4. 需要并行探索多个假设，再汇总比较。

拆分顺序，每一步都要用评测指标验证收益，没有提升就退回：

1. 单 agent + 工具循环 + 证据校验（现有 `runtime.py` 的能力）；
2. 加 planner：先决定查哪些数据源，减少无效工具调用；
3. 拆专家子图：资产、知识、历史工单各自工具集和权限；
4. 加独立 critic：拦截无证据结论、危险建议、越权操作。

跨步骤的多 agent 不画进一张 LangGraph 图，建模成业务流程里的多个 agent
节点，由外层引擎推进。这样「多个 agent」和「跨天等待」不会挤在同一层。

### 7. 进程内协作，不使用 A2A

本项目的多 agent 都在同一个进程、同一次 `run()` 内：共享工具和状态，
直接函数或子图调用。A2A 面向跨进程、跨组织、需要能力发现和任务委派的
场景，这里没有对端，也没有跨厂商需求；引入它只会增加网络、身份、
序列化与版本协商的成本。

将来如果要接外部团队或厂商提供的 agent（例如厂商保修查询），那属于
外部系统集成，走防腐层（Backend 接口 + Adapter），和接 GLPI API 同级，
不放进内部的多 agent 图。

MCP 同理：它解决 agent 与工具/数据源之间的协议，接 GLPI 工具时可以用，
但不是必须。当前 `ToolExecutor` 函数已经够用，等工具需要跨进程时再考虑。

### 8. 第一个复杂场景：故障诊断

选择理由：与现有报障受理同域，可复用 StepResult、verify、工具 schema 和
外层引擎；数据源天然只读；有明确的评测标准。

```
外部流程
  收症状（wait_user，可能多轮）
  → agent 节点：诊断（内部 LangGraph）
      planner -> 资产 / KB / 历史工单 / 监控（可并行）
      -> hypothesis（每个根因带工具证据）
      -> verifier（证据可追溯、置信度分级）
      -> critic（危险建议、越权、该不该转人工）
      -> StepResult + 诊断报告
  → 自助建议 / 建单给工程师 / 追问
  → 等解决或关闭，记录结果用于评测
```

第二个场景：从已解决工单生成 KB 草稿（聚类、提取步骤、去重、引用校验、
人工审核发布）。它练离线归纳与内容质量评测，与故障诊断互补，排在后面。

### 9. 评测是验收条件

没有评测的多 agent 只是 demo。故障诊断先建 20-30 个标注案例，覆盖：

- 症状 + 资产特征 + 历史工单能定位根因；
- 症状 + KB 能给出自助步骤；
- 症状模糊，正确动作是追问而不是猜；
- 证据不足或建议有风险，正确动作是转人工。

指标：根因命中率、证据可追溯率、误转人工率、危险建议率。
`ScriptedChatModel` 跑回归，真实模型跑抽样。

两层轨迹用 `step_execution.key` 关联：外层记录每步的 `StepResult` 和 outcome，
内部记录每轮模型输出、工具调用、校验结果。回放时先看外层走到哪个节点、
返回什么动作，再看内部为什么返回这个动作。这是区分「流程错」和「模型错」
的唯一办法。

### 10. 两个实现的分工

`SingleAgentRuntime` 冻结在切片 3b 的行为，只作为对照与回退：允许修 bug、
跟随共用函数重构，不再增加新能力（并行、子图、新预算都不加）。
`LangGraphRuntime` 是唯一继续生长的实现，3c / 3d 的新结构只加在这里。

理由是两份实现已经让路由和预算逻辑各有一份副本；3c 加入并行数据源和
专家子图后，「行为一致」不再是目标，如果两边都长，每次改动都要写两遍、
再维护一套对照用例。对照用例保留到 3c 评测结束，用评测结果决定删掉
还是留作回归基线。

## 切片划分

| 切片 | 内容 |
|---|---|
| 3a | `AgentRuntime` 接口；现有 runtime 适配到接口，行为不变，测试全过 |
| 3b | LangGraph 实现，跑同一套 runtime 用例；两层轨迹记录 |

2c（定时器、事件源、回放）推迟，等接 GLPI 真实事件时再做。

## 未决

1. 是否长期保留非 LangGraph 实现作为回退（当前倾向保留，评测时作为对照）。
2. 内部轨迹的存储格式与保留策略。
3. 多 agent 子图之间的上下文传递契约（共享 state 还是显式输入输出）。
4. LangGraph 版本锁定与升级策略。
5. 故障诊断的数据源在本地如何伪造（FakeAdapter 的资产/监控/KB 形状）。
