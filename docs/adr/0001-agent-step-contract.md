# ADR 0001：单步 Agent 的输出契约

- 状态：草案（切片 1）
- 日期：2026-11-08

## 背景

Agent 的每一步（一次工具调用、一次建单请求、一次检索）都要向上游交回一个结果。
上游是流程引擎，它必须只根据这个结果就能决定下一步，不需要知道 GLPI 错误码。

## 决策

### 1. 动作是唯一的分支依据

每一步的结果归入五类动作之一：

| 动作 | 含义 | 上游做什么 |
|---|---|---|
| `need_input_fix` | 输入不合法，未作任何外部请求 | 回到对话追问或修正参数 |
| `retryable` | 失败，且确定没有副作用 | 可安全重试 |
| `need_human` | 需人工介入 | 转人工；原因随结果带过去 |
| `succeeded` | 成功且符合预期 | 继续流程 |
| `succeeded_needs_review` | 成功，但结果与预期不一致 | 继续流程 + 记录冲突 + 通知 |

### 2. 副作用字段表达「可能已发生」，不表达事实

字段名 `may_have_committed`，二值。

- 请求没发出去 → `False`
- 已发出、结果未知 → `True`
- 确定建成 → `True`
- 明确被拒 → `False`

理由：不可观测时字段表达最坏情况，所有消费方自动保守。
「未知」与「确定发生」的区分只用于日志和排查，不参与任何动作，因此放在 `cause` 里。

替代方案（未采用）：三值字段（未发出 / 结果未知 / 已发生）。信息更全，但每个消费方都要处理第三态，容易漏。

### 3. 不变量

| 动作 | `may_have_committed` | 理由 |
|---|---|---|
| `need_input_fix` | 必须 `False` | 输入没过校验，请求不可能已发出 |
| `retryable` | 必须 `False` | 否则重试会重复建单 |
| `need_human` | 不约束 | 发出前被拒（403）或发出后结果未知（超时） |
| `succeeded` | 不约束 | 只读步骤（查资产）成功也无副作用 |
| `succeeded_needs_review` | 不约束 | 同上 |

违反不变量的结果在构造时就抛错，不交给上游检查。

**修订记录**：初版把 `succeeded` 定为必须 `True`，前提是「成功必然意味着有副作用」。
写 runtime 时发现它只对写步骤成立——切片 1 的步骤是「生成建单草稿」，
成功时什么都没提交，被这条不变量错误地拦下。

结论：不变量只该拦「放过去会出事」的组合，不该表达「语义上应该如此」的
组合。后者会误杀合法场景，而前者是安全底线。

### 4. 原因只做观测

`cause` 是结构化字段，用于人工处置和统计，不参与分支。
错误码 → 动作的映射只在适配层存在一份；展示层只把动作映射成文案档位。

### 5. 允许选择，禁止生成

模型可以从工具结果中指认某个值，不能自己造值。
证据校验在输入侧完成：判断模型给出的值是否等于证据中某个工具返回项的值。

### 6. 工具必须带参数 schema

工具只有自然语言描述时，模型会自己发明参数名。实测：模型传 `{"serial": "SN12345"}`，
执行器读 `arguments["q"]` 读不到，返回空列表；模型把空列表当成「查无记录」，
于是告诉员工「没查到这台设备」——一次完全错误的结论，没有任何报错。

规则：

- 每个工具必须有 JSON Schema 形式的参数定义，同时用于 prompt 展示和执行前校验。
- 参数不符合 schema 时不执行，记一条失败调用，把错误摘要回给模型重试。
- 「尚未调用过工具」和「调用过但返回空」在 prompt 里必须用不同渲染表达，
  否则模型会把 `[]` 读成「查过了，没有」。

### 7. 追问用结构化意图，不用自由文本

模型只输出「要问什么」，句子由代码模板生成：

| kind | 必须携带 | 校验规则 |
|---|---|---|
| `missing_field` | `field`（输出 schema 的 key）+ `label`（≤20 字的短名词短语） | field 必须在 schema 里；label 不能是整句 |
| `no_result` | 一个 `call_id` | 该调用必须成功且返回空——没查过就不许说没查到 |
| `ambiguous_asset` | 每个候选的 `ValueRef` | 每个候选都必须能追溯到工具结果 |

理由：对员工说的话是风险最高的输出，而自由文本无法逐句校验。实测中模型
在只调过一次工具、且该调用返回空之外的情形下，说过「用序列号没查到」。
结构化之后，这句话在结构上就说不出来。

代价：表达自由度下降，一些细腻的追问表达不了；新增追问类型需要改代码。
这是有意的——新增类型是一次显式设计动作，而不是模型的自由发挥。

## 未决

1. `evidence` 的结构（目前是字符串元组，需要定义工具调用记录的形状）。
2. 结果未知时的核对机制（幂等键、幂等表、向 GLPI 查重），见后续 ADR（幂等语义）。
3. 步骤的输入形状（对话上下文、身份、已提取字段如何进入这一步）。
